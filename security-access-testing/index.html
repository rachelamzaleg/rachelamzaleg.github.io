PRACTICAL QA GUIDE

Access Granted. But Is It Actually Secure?

Authorization testing goes beyond a successful login: check denied actions, changing policies and the evidence left across the system.

Map the decision points

Identify who is requesting access, which resource is involved, which policy applies and where enforcement happens. Include both direct access and access through gateways or integrated services.

Build a small permission matrix

Cover an authorized user, an unauthorized user, a user with changed permissions and an expired or invalid session. Add policy conflicts and default-deny behavior where relevant.

Check the full result

A blocked request should not create an unintended database change or expose sensitive data in a response. A permitted request should complete successfully and produce the expected audit event.

Test transitions, not just static states

Check what happens after login, logout, permission changes, policy updates and reconnection. Validate whether changes take effect at the expected stage of the request.

Capture evidence safely

Record request outcomes, relevant audit entries and reproducible steps. Avoid placing credentials, tokens or personal data in test reports.

Access policy test design

Build a focused test matrix for allowed and denied users, permission changes, expired sessions, conflicting policies and audit events. Check database effects and unintended data exposure.

Rules: Ask focused questions when information is missing. Do not treat hypotheses as facts, invent test results, or request secrets. Propose the next step and wait for my response.

Hands-on execution: If suitable tools are available, do not stop at proposing tests. Run safe read-only checks yourself: API requests, existing test scripts, read-only log and database queries, and browser checks as appropriate. Start with small targeted tests, show the command or action executed and its actual output, and adapt the next step to the evidence. If a required tool is unavailable, say so explicitly and provide a command or test case I can run.

Ask for explicit approval before writes, configuration changes, data deletion, impactful processes, or testing in production. Never report a proposed test as executed, and never assert a root cause without evidence.
