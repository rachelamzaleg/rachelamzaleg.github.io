Claude Reported a Bug? Verify the Evidence

Separate observed evidence from assumptions, establish a working baseline and know when to stop for verification or approval.

1. Prove the baseline

Check the simplest officially supported setup without the change under test. Confirm that it works before interpreting a failure.

2. Verify before diagnosing

Confirm the reported symptom. Reproduce where possible, compare passing and failing behavior, and document the affected areas. Keep hypotheses separate from observed facts.

Unexpected failure? Stop at the failing step and show the evidence. Do not silently bypass it or invent a root cause.

3. Use clear approval gates

  • Routine work: drafts, local notes, independent reviews and authorized read-only checks.
  • Approval required: live configuration changes, live browser automation, destructive actions and posting to test trackers or stakeholders.
  • Human judgment: whether unexpected behavior is a bug, intended design or not yet understood.

4. Review significant artifacts

Use a separate validator to identify gaps, assumptions and contradictory evidence in stakeholder-facing artifacts. Skip unnecessary orchestration for small internal tasks.

Evidence and approval checkpoints

Help review a QA finding. Separate observations, hypotheses and missing evidence. Ask for a passing baseline and reproduction evidence, propose a discriminating check, and flag decisions that require approval.

Rules: Ask focused questions when information is missing. Do not treat hypotheses as facts, invent test results, or request secrets. Propose the next step and wait for my response.

Hands-on execution: If suitable tools are available, do not stop at proposing tests. Run safe read-only checks yourself: API requests, existing test scripts, read-only log and database queries, and browser checks as appropriate. Start with small targeted tests, show the command or action executed and its actual output, and adapt the next step to the evidence. If a required tool is unavailable, say so explicitly and provide a command or test case I can run.

Ask for explicit approval before writes, configuration changes, data deletion, impactful processes, or testing in production. Never report a proposed test as executed, and never assert a root cause without evidence.
