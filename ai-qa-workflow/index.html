How I Work with AI in QA

I structure AI-assisted QA around evidence, focused responsibilities and human decisions. The goal is not to automate judgment: it is to make analysis, validation and repeated work more consistent and easier to reuse.

Evidence before conclusionsHuman-led decisionsReusable learning

One QA practice, two outcomes

The same collaboration helps deliver the QA work—understanding changes, planning coverage, checking behavior and reporting results—and improve the process behind it. When a recurring correction reveals a weakness in the workflow, I turn the lesson into a specific reusable rule or skill.

The assistant supports the work. I own the scope, technical judgment, approvals and final conclusions.

The workflow: from change to verified result

Each step is grounded in requirements, live product behavior or recorded evidence. The sequence stops when a real problem needs my decision.

  1. Prepare the contextEstablish the feature scope and verified environment baseline.
  2. Analyze the changeClarify expected behavior, affected components and risks.
  3. Define test coveragePrioritize scenarios, boundaries and integration paths.
  4. Draft executable casesWrite concise, customer-oriented cases with clear checks.
  5. Run live checksUse verified scripts or APIs first; inspect UI and logs as needed.
  6. Record and reportUse actual results and live tracking data—not an old summary.
Unexpected behavior? Stop and bring evidence.

No silent workaround, no assumed root cause and no automatic “bug or by design” verdict. I decide the next step.

Checks completed as expected?

Record the observed result and prepare a concise status update from the live source of truth.

Improvement loop

Correction → Retrospective → Update one reusable source → Review and commit

A repeated mistake should change the process that caused it, not merely the latest draft.

Separate responsibilities, not uncontrolled agents

I use focused AI roles as a way to structure the work. They are responsibilities, not a claim that five autonomous agents always run together.

CoordinatorClarifies direction, keeps work in scope and manages checkpoints.
DocumentationDrafts test cases, bug reports, test scope and summaries from evidence.
ValidatorChallenges omissions, assumptions and contradictions without silently rewriting the draft.
Hands-on QAChecks real environments, APIs, data, configuration and observed behavior.
StatusBuilds updates from current tracker results, not copied status files.

Stakeholder-facing drafts receive a separate review pass; lightweight internal tasks do not need unnecessary orchestration.

Practical safeguards

Evidence first

Confirm a clean baseline, verify the claim, reproduce where possible and compare passing with failing conditions before narrowing conclusions.

Explicit approval

External updates, live changes, browser actions and destructive operations wait for my authorization. Drafting and read-only checks can stay lightweight.

One fact, one home

Skills hold repeatable methods; references hold product facts; task notes hold local context. Live tracking systems remain the source of status.

Lean context, full capability

Read the relevant section, not every log or document. Use targeted evidence and reset accumulated context at useful milestones.

How a correction becomes a practice

Stop on the first meaningful failure

When a setup step fails, completing the rest of the checklist can hide the original problem. My rule is to stop, describe the actual failure and ask whether to investigate, repair the baseline or change direction. If that pattern recurs, I update the reusable procedure so the next run follows the better checkpoint.
