Repeating Browser Steps? Claude Should Notice

While working, Claude recognizes repeatable flows, checks for APIs or existing scripts, and turns verified sequences into reusable tasks.

1. Choose the lowest-overhead path

When a browser task comes up, start with the product API. If it needs UI interaction, reuse an existing verified script. Explore interactively only when necessary and approved.

API first — use supported endpoints for the task.
Saved script second — run a repeatable Playwright check.
Interactive browser last — request approval before exploring.

2. Turn exploration into reusable execution

Once the UI flow works, preserve it as a Playwright script. Run recurring checks without repeatedly feeding a full browser state into Claude. Use a post-run script for routine result handling.

3. Use hooks as guardrails

Hooks help enforce boundaries at defined points in a workflow. Keep the rules consistent while scripts handle deterministic actions. Use AI for unexpected outcomes that require technical judgment.

4. Understand the context cost

~2,000tokens for eight saved tasks
~16,000tokens for one browser snapshot loaded into context

Illustrative figures for different workloads, not a like-for-like savings benchmark.

5. Keep quality in the loop

A faster execution path is only useful when results can still be checked. Capture failures and evidence, review unexpected behavior, and use measurable comparisons before making percentage-savings claims.

Engineering principle: Automate predictable tasks with scripts. Use AI where analysis and judgment add value.

Standing rule: Detect repeated browser work and reuse scripts automatically

During any QA task, watch for browser action sequences that repeat or are likely to be needed again. Do not wait for me to request this analysis or ask me to describe a recurring browser test upfront.

Follow this workflow:
1. Carry out the current task using available authorized tools.
2. Before repeating interactive browser steps, check whether an API or existing script can do the job more reliably and simply.
3. If Playwright exploration is needed, execute it and verify the actual result.
4. When you recognize a stable sequence worth reusing, suggest turning it into a script-based task. Briefly explain what will be preserved and why. Do not script every one-off action.
5. After approval, create a Playwright script with defined inputs, assertions, error handling, logs and a short run command. Save it with usage instructions.
6. On future tasks, prefer the existing script. Return to interactive exploration when the flow changes, the script fails or new evidence requires investigation.

Run safe read-only checks when authorized tools are available, and report what actually ran and returned. If tools are unavailable, say so and prepare a runnable check. Ask permission before data or configuration changes, production tests or impactful actions. Never present an unexecuted test as completed or claim measured token savings without measurement.
