How to Use Claude in QA Investigations

Claude can save a lot of time in QA investigations. The trick is to give it the right information and use it to help you think — not to let it decide what the bug is.

Start with the problem

Do not start by pasting a huge log and asking “what is wrong?”. First explain the issue in a few clear lines.

  • What should happen?
  • What actually happens?
  • How do you reproduce it?
  • Which parts of the system are involved?
  • What have you already checked?
Claude works much better when the problem is clear before the logs arrive.

Give only the useful evidence

Add the logs, config, SQL results, API responses or timestamps that are relevant to the failure. If there is too much data, send it in parts.

I usually ask Claude to first summarize what it sees and separate facts from guesses. That already helps find gaps and contradictions.

Ask for a few possible causes

Do not ask Claude for “the root cause”. Ask for several possible causes and what would prove or disprove each one.

Here is the issue and the evidence. Give me 3-5 possible causes. For each one: - what evidence supports it - what does not fit - what should I check next Do not assume information I did not give you.

Check one thing at a time

Once there are a few good options, test them. Change one thing at a time and see what happens.

For example: different credentials, fresh token, different config, new connection, service restart, another database state or a different request timing.

This is the important part: Claude can suggest what to check, but the real system result is what decides.

Use Claude to connect the dots

In system QA the answer is often spread across several places. One event appears in the client, another in the service log, another in the database and another in authentication.

Claude is useful for putting these events in order and showing where the flow starts to look wrong. Then I go back and verify it in the real data.

Turn the bug into better tests

After the problem is understood, use the same information to ask: what test was missing?

Claude can help suggest regression tests, negative cases and edge cases based on the actual bug — not just produce a long generic test list.

Automate only what is worth it

Claude can also help create a small script, SQL check, API validation or repeated test. I do not try to automate everything. If a simple check saves time and catches a real risk, that is enough.

A simple prompt I can reuse

Help me investigate this QA issue. I will give you: - expected result - actual result - reproduction steps - relevant logs/config/data - what I already checked Please: 1. summarize the facts 2. list the most likely causes 3. tell me what information is missing 4. suggest the next checks, one by one 5. do not invent missing details 6. after we confirm the cause, suggest regression tests

The rule I keep

Claude is there to save time, organize information and help me think of things I may have missed. I still verify everything against the real system before I decide what happened.
