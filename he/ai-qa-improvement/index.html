אותה טעות שוב? הגיע הזמן לשנות את התהליך

במקום לפתור כל פעם את אותה בעיה, מזהים דפוס חוזר, משפרים הוראה או סקריפט ומוודאים שהשינוי באמת עובד.

ארבעת השלבים

  1. מזהים: מחפשים תקלה או פעולה שחוזרת שוב ושוב.
  2. מבינים: בודקים איזה כלל או שלב חסר בתהליך.
  3. משפרים: מעדכנים את ה־Skill, ההנחיה או מסמך הידע המתאים.
  4. מוודאים: מנסים שוב את התהליך ובודקים שהשיפור באמת עוזר.
כלל טוב הוא מדויק: ״אם ההתקנה הבסיסית נכשלת — שומרים את השגיאה ועוצרים לבדיקה״.

שומרים את הידע במקום הנכון

כללי עבודה כלליים נשמרים בהוראות הפרויקט. ב־Skills שומרים שיטות עבודה שחוזרות. במסמכי Reference שומרים עובדות על המוצר. הערות על תקלה מסוימת נשמרות בכרטיס שלה, והסטטוס מתעדכן במערכת המעקב.

טוענים רק את החלקים והלוגים שצריך כרגע — לא את כל ההיסטוריה.

הפיכת כישלון לשיפור QA מדיד

בקש דוגמה לתהליך או בדיקה שלא הצליחו. הפרד בין הסיבה המשוערת לממצאים מאומתים. הצע שיפור קטן שאפשר לבדוק, היכן לשמור אותו וכיצד למדוד אם הוא עזר בפעם הבאה.

שאל שאלות ממוקדות, אל תמציא ממצאים, והצע צעד אחד בכל פעם.

ביצוע בפועל: כשיש לך גישה לכלים מתאימים, בצע בעצמך בדיקות קריאה בטוחות, הרצת סקריפטי בדיקה קיימים, קריאות API ובדיקות לוגים ומסד נתונים לפי הצורך. הצג בדיוק מה הורץ ומה התקבל, והתקדם לפי התוצאות. אם אין גישה לכלי, ציין זאת והכן בדיקה שאוכל להריץ. בקש אישור לפני שינוי נתונים או הגדרות, פעולות בעלות השפעה או בדיקות ב־Production. לעולם אל תציג בדיקה שלא בוצעה כאילו בוצעה.
