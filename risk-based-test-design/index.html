TEST DESIGN · RISK PRIORITIZATION

More Test Cases Don't Mean Better Coverage

Claude can generate dozens of scenarios. Good QA design decides what threatens the product, what must run first, and what can wait.

New feature? Start with its Confluence documentation

For a new feature, start with its dedicated Confluence page: feature description, product specification, design, configuration, diagrams, acceptance criteria and linked development tickets. Read comments, discussions, decisions and later updates too; they may change expected behavior.

Distinguish a completely new capability from an extension or modification of existing behavior. Compare against the current system, map integrations and dependent components, and identify what must continue working. Flag conflicting documents or unresolved decisions before setting expected results.

Build a traceable test document linking Confluence requirements and decisions to risks, scenarios and expected outcomes. This also helps colleagues understand why tests were selected and what remains open.

Build from the company's existing knowledge

Before drafting cases, Claude should gather and cross-check authorized internal sources: product specifications, design and architecture documents, system configuration, development tickets, previous test plans, known defects and colleagues' documentation. A single feature summary is not enough.

Map current behavior against the proposed change: what existed, what changes, what remains unchanged, and whether this is a completely new capability or an extension of an existing one. Identify dependent components, integrations, business flows and regression impact.

Trace significant requirements to their sources and versions or update dates when available. Flag conflicts between specs, design, existing behavior and earlier documentation for Product, R&D or QA to resolve rather than inventing expected behavior. Make the resulting test document useful to colleagues: change context, validated assumptions, prioritization rationale, coverage, gaps and source links.

Start with the change, not a test-case list

Clarify what changed, who is affected, expected behavior, dependencies and the consequences of failure. Flag missing information rather than filling gaps with assumptions.

Rank risk before expanding coverage

Consider potential impact (severity), likelihood and exposure separately. Focus on core journeys, security and access, integrations and data integrity. Not every edge case deserves equal attention.

Make the test document actionable

For each case capture an ID, requirement or risk, preconditions, steps, expected result, risk and execution priority. Group as P0 (release-critical), P1 (core coverage) and P2 (extensions or regression as time permits). Priorities depend on context, not an automatic formula.

Avoid AI-generated test bloat

Ask Claude to identify duplicates, consolidate similar cases and justify each test's unique value. Do not let dozens of low-impact variations crowd out core flows or high-consequence failures. Negative tests matter when they address a real risk.

What runs first, and what waits?

Verify the baseline and critical paths first, then high-risk changes, cross-component boundaries and sensitive behavior. Extend to edge cases and broader regression later. Adjust for dependencies, available time and emerging findings.

Claude can execute, too

Where authorized tools exist, Claude can run safe checks, collect evidence and record actual outcomes. Distinguish Not Run, Passed, Failed and Blocked. Never fabricate execution results; obtain approval before impactful changes.

Ready-to-use prompt: risk-based test plan

Copy and adapt to your product and environment.

For a new feature, begin with its dedicated Confluence page and linked materials. Review specs, design, configuration, acceptance criteria, comments, discussions, decisions and updates. Identify what is new, what changes from current behavior, affected components and required regression coverage. Trace tests to documented requirements or decisions and flag conflicts and open questions. If Confluence is unavailable, ask for the relevant link or content; do not claim to have read it.

Required first step — internal evidence gathering: Search available authorized company sources for product specs, design, architecture, configuration, development tickets, prior test plans, defects and colleagues' documentation or decisions. Cite source links when available. Do not assume access to unconnected systems or fabricate missing facts. Build a current behavior / planned change / entirely new capability / unchanged behavior / cross-component impact map. Flag contradictions and gaps for the relevant owners before defining expected outcomes. Make the final document useful to colleagues by preserving context, sources, validated assumptions, prioritization decisions, coverage and open gaps.

Act as a senior risk-based QA test designer and execution partner. Do not start by generating a long list of test cases.

1. Clarify the change, requirements, affected users and flows, environment and time constraints. Ask targeted questions only for material gaps.
2. First produce a concise risk map: possible failure, impact/severity, likelihood, exposure, dependencies and confidence. Separate facts from assumptions.
3. Draft a lean test document with ID, requirement/risk, scenario, preconditions, steps, expected result, P0/P1/P2 execution priority and a brief reason.
4. Order tests by what must run first, next and later. Distinguish failure severity from execution priority.
5. Review your own output: remove duplication, trim low-value variations and ensure coverage of core flows, permissions, data and integrations. Briefly note what was deferred and why.
6. When suitable authorized tools are available, execute safe checks, show evidence and mark Passed/Failed/Blocked/Not Run based only on real results. Ask approval for impactful actions.
7. Reprioritize when evidence or risk changes. Do not inflate test counts to imply coverage.
